# Redis Cluster 原生集群：分片、复制与自动故障转移

> 主题边界：纵向机制篇——展开官方原生 Redis Cluster 的数据分片、主从复制、在线重新分片与自动故障转移。方案选型定位见 [redis-cluster-overview.md](./redis-cluster-overview.md)，与哨兵模式的逐项对比见 [redis-sentinel.md](./redis-sentinel.md)。

---

## 1. 总述

Redis Cluster 是 Redis 3.0 之后官方推出的原生分布式集群方案，互联网和大型企业项目中最广泛采用的标准方案。

- **核心特点**：无中心化 P2P 架构，16384 个哈希槽（SLOT）动态分片，节点间 Gossip 协议通信
- **优势**：无代理层，性能损耗极低；原生支持自动故障转移和在线扩缩容（Resharding）
- **局限**：需要客户端支持集群协议（Smart Client）；不支持跨槽多 Key 操作
- **适用场景**：高并发、大数据量、需要水平扩展的生产环境

集群同时提供**数据分片、主从复制和自动故障转移**三种能力，无须再部署 Sentinel。

## 2. 数据分片：哈希槽只分配给主节点

每个主节点都可以挂载 0 个、1 个或多个从节点，生产环境通常建议每个主节点至少配置 1 个从节点。以常见的 **3 主 3 从** 架构为例：

```text
M1（哈希槽 0～5460）      → R1
M2（哈希槽 5461～10922）  → R2
M3（哈希槽 10923～16383） → R3
```

- 16384 个哈希槽按 Key 的 CRC16 值取模分配，槽只分配给主节点
- 从节点不固定拥有哈希槽，而是通过**异步复制**保存对应主节点的数据，用于故障接管
- 客户端需支持集群协议（Smart Client），本地缓存槽位映射，直连目标主节点读写

## 3. 在线重新分片（Resharding）

扩容或缩容主节点时，通过迁移哈希槽及其数据重新分配负载：

- 从节点持续复制所属主节点当前负责的数据，**无须单独为从节点分片**
- 迁移期间集群仍可提供服务，支持集群协议的客户端通过 `MOVED`、`ASK` 重定向访问目标节点
  - `MOVED`：槽已稳定归属新节点，客户端应更新本地槽位映射
  - `ASK`：槽正在迁移中，本次请求临时转向目标节点，不更新映射

## 4. 自动故障转移

主节点故障后，满足集群故障判定并获得**多数主节点授权**时，其从节点会被提升为新主节点，接管原主节点的哈希槽。整个流程由节点间 Gossip 协议投票自动完成，无需外部组件。

- **高可用限制**：也可以只部署主节点，但主节点宕机且没有可接管的从节点时，其负责的哈希槽将无法正常服务

## 5. 读写方式与部署建议

- **读写方式**：客户端默认读写主节点；可以使用 `READONLY` 允许从从节点读取，但由于复制是异步的，可能读到旧数据
- **部署建议**：支持一主多从，例如 3 主 6 从；主从节点应尽量部署在不同机器、机架或可用区，避免同时故障
