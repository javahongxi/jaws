# Redis 持久化详解：RDB、AOF 与混合持久化

> 主题边界：持久化机制篇——展开 RDB 快照、AOF 日志与混合持久化的原理、取舍与生产实践。持久化"为什么不在写路径上"的性能视角见 [redis-why-fast.md](./redis-why-fast.md) §5，集群与复制背景见 [redis-cluster.md](./redis-cluster.md)。
> 口径：机制描述以 Redis 6.x/7.x 为准，涉及版本演进处单独标注；无源码行号锚点，属原理分析而非逐行精读。

---

## 0. 总述：三句话答案

1. **RDB 是快照**：某一时刻全量数据的二进制压缩副本，恢复快、适合备份，但两次快照之间的数据会丢。
2. **AOF 是日志**：逐条记录写命令，数据安全性高（everysec 最多丢约一秒），但文件大、恢复慢。
3. **混合持久化取两者之长**：AOF rewrite 时基座用 RDB 格式、增量用 AOF 命令——恢复速度接近 RDB，数据安全接近 AOF，是 4.0 之后的推荐形态。

Redis 默认**只开 RDB、不开 AOF**（`appendonly no`）。纯缓存场景可以两者都关；有数据安全诉求就开 AOF + 混合持久化。下面按 RDB、AOF、混合持久化、恢复与选型、生产陷阱五面展开。

## 1. RDB：全量快照

### 1.1 生成方式

| 方式 | 行为 | 阻塞 |
|---|---|---|
| `SAVE` | 主线程直接生成快照 | 全程阻塞，生产禁用 |
| `BGSAVE` | fork 子进程生成快照 | 仅 fork 瞬间停顿 |
| `save m n` 配置 | m 秒内至少 n 次修改自动触发 BGSAVE | 同 BGSAVE |
| 主从全量同步 | 主节点 BGSAVE 生成 RDB 发给从节点 | 同 BGSAVE |
| 正常关闭（SHUTDOWN） | 自动执行一次 SAVE | 退出前阻塞 |

- 默认触发点（6.0 起）：`save 3600 1 300 100 60 10000`——1 小时 1 次修改 / 5 分钟 100 次 / 1 分钟 1 万次，任一满足即触发。
- 文件为二进制 + LZF 压缩（`rdbcompression yes`），紧凑、适合传输与冷备。

### 1.2 fork + 写时复制（COW）

BGSAVE 的核心是**fork 出子进程共享父进程内存页表**：

- 子进程看到的内存是 fork 瞬间的一致视图，遍历写盘即可，主进程继续服务写请求。
- 主进程修改某页时触发**写时复制**：内核复制该页，子进程仍读旧页——快照一致性由内核保证，无须加锁。
- 代价集中在两处：**fork 瞬间拷贝页表**（内存越大越久，GB 级内存约毫秒到几十毫秒停顿）；**COW 额外内存**（快照期间写入越密集，复制页越多，极端情况内存翻倍）。

### 1.3 优劣

- **优势**：文件紧凑、恢复是"整块加载"速度极快；适合定时冷备、异地容灾、主从全量同步。
- **局限**：两次快照之间的数据全部丢失；fork 在大内存实例上有可感知毛刺。

## 2. AOF：写命令日志

### 2.1 写后日志（write back）

AOF 记录的是**已执行的写命令**（RESP 文本格式），流程是：命令执行成功 → 追加进 `aof_buf` → 事件循环末尾 write 进内核页缓存 → 按策略 fsync 落盘。

与 MySQL redo log 的"写前日志（WAL）"相反，Redis 选择**先执行后记录**：

- 省掉语法检查开销——能记进日志的一定是执行成功的命令；
- 不阻塞当前命令的执行——落盘成本后置；
- 代价：执行与落盘之间的窗口内宕机会丢命令，丢失量由 fsync 策略决定。

### 2.2 三种 fsync 策略（appendfsync）

| 策略 | 行为 | 数据安全 | 性能 |
|---|---|---|---|
| `always` | 每条命令同步 fsync | 最多丢一条命令 | 最差，fsync 回到关键路径 |
| `everysec`（默认） | 后台线程每秒 fsync 一次 | 最多丢约一秒数据 | 折中，写路径只到页缓存 |
| `no` | 由内核决定何时刷盘（约 30s） | 丢失量不可控 | 最好 |

- everysec 的 fsync 由后台 bio 线程执行，但主线程 write 前会检查上一次 fsync 是否完成：**未完成则推迟本次 write**——磁盘失速时主线程仍可能被拖住（最长约 2 秒），这是 everysec 并非绝对无阻塞的原因。
- `no-appendfsync-on-rewrite`（默认 no）：rewrite 期间是否暂停 fsync，开启可避免磁盘竞争加剧毛刺，代价是窗口内丢失量变大。

### 2.3 AOF 重写（rewrite）

AOF 逐条追加会无限膨胀（对同一个 Key 的 100 次 SET 只留最后一次即可）。重写**不读旧 AOF**，而是 fork 子进程按内存当前状态生成最小命令集：

- 触发：`BGREWRITEAOF` 手动；或 `auto-aof-rewrite-percentage 100` + `auto-aof-rewrite-min-size 64mb`（文件比上次重写后大一倍且超过 64MB）自动。
- **7.0 之前的痛点**：重写期间新写命令要双写进 `aof_buf` 与 `aof_rewrite_buf`，子进程收尾时把 rewrite 缓冲追加进新文件——双份内存开销 + 收尾合并阻塞。
- **7.0 Multi-Part AOF**：AOF 拆成**基座文件（base）+ 增量文件（incr）+ 清单文件（manifest）**。重写期间新命令直接写新的 incr 文件，彻底消除 rewrite 缓冲与收尾合并——重写从"双写 + 合并"变成"换个文件继续写"。

## 3. 混合持久化（4.0 起，aof-use-rdb-preamble yes 默认开启）

AOF 重写时，子进程把内存状态以 **RDB 二进制格式**写成基座，重写期间的增量仍以 AOF 命令追加：

- 文件形态 = RDB 头 + AOF 尾（7.0 后对应 base 文件可为 RDB 格式 + incr 文件）；
- **恢复速度接近 RDB**（大头是二进制整块加载），**数据安全接近 AOF**（增量命令补齐）；
- 代价：基座部分不再可读，人工审计 AOF 文本的能力减弱。

## 4. 恢复顺序与选型

### 4.1 重启加载顺序

开启 AOF 时**优先加载 AOF**（数据更完整），未开启才加载 RDB；两者都没有则以空数据集启动。RDB 的不可替代场景是冷备恢复与主从全量同步。

### 4.2 对比与选型

| 维度 | RDB | AOF（everysec） | 混合持久化 |
|---|---|---|---|
| 数据形态 | 二进制全量快照 | 文本写命令日志 | RDB 基座 + AOF 增量 |
| 丢失窗口 | 上次快照以来全部 | 约一秒 | 约一秒 |
| 恢复速度 | 快 | 慢（逐条重放） | 接近 RDB |
| 文件体积 | 小（压缩） | 大（重写收敛） | 中 |
| 典型用途 | 冷备 / 容灾 / 全量同步 | 数据安全兜底 | 生产默认推荐 |

- **纯缓存**（数据可重建）：可关闭全部持久化，或只留 RDB 供重启快速回暖。
- **有数据安全诉求**：AOF everysec + 混合持久化，同时保留定时 RDB 冷备（异地/对象存储）。
- **极端安全**：appendfsync always，吞吐骤降，极少采用——真要强持久性应选数据库而非 Redis。

## 5. 生产实践与陷阱

- **fork 毛刺**：与内存量成正比，大实例建议控制单分片内存（配合 Cluster 分片，见 [redis-cluster.md](./redis-cluster.md)）；监控 `latest_fork_usec`。
- **透明大页（THP）**：开启后 COW 复制单位从 4KB 变 2MB，写时复制放大数百倍，延迟与内存双恶化——生产建议关闭 THP。
- **内存余量**：COW 极端情况内存翻倍，需预留余量；`vm.overcommit_memory=1` 避免 fork 因内存记账失败。
- **磁盘写满**：`stop-writes-on-bgsave-error yes`（默认）下 BGSAVE 失败会**拒绝所有写命令**——磁盘水位必须监控，这是"持久化配置反噬可用性"的典型。
- **AOF 损坏**：尾部截断可用 `redis-check-aof --fix` 修复（丢弃尾部不完整命令）；`aof-load-truncated yes`（默认）允许加载截断的 AOF 并告警。
- **主从分工**：可在从节点开 AOF、主节点只留 RDB，把 fsync 压力挪出主节点——但主节点宕机切换窗口内的丢失量要按业务评估。
