# Redis 为什么快：高性能成因分析

> 主题边界：横向综合篇——不重复集群与缓存问题的细节，只回答一个问题：**一条 GET/SET 命令的固定成本（寻址、并发控制、IO、协议解析）去了哪里，被谁省掉**。集群方案见 [redis-cluster-overview.md](./redis-cluster-overview.md)，缓存三大问题见 [redis-cache-penetration.md](./redis-cache-penetration.md) 系列。
> 口径：机制描述以 Redis 6.x/7.x 为准，涉及版本演进处单独标注；无源码行号锚点，属原理分析而非逐行精读。

---

## 0. 总述：三句话答案

1. **把数据放进内存**：读写不碰磁盘，一次内存寻址约百纳秒级，比磁盘 IO 低几个数量级——这是快的物理基础。
2. **把并发成本省掉**：命令执行单线程 + IO 多路复用，没有锁竞争、没有上下文切换、没有竞态条件——这是快的模型基础。
3. **把每条命令的固定成本压到极低**：O(1) 哈希寻址、紧凑数据结构、简单 RESP 协议、持久化挪出关键路径——这是快的工程基础。

单实例 GET/SET 可达约 10 万 QPS 量级（Pipeline 下更高）。快不是"某个优化很猛"，而是**每一层都在做同一件事：让关键路径上只剩内存操作**。下面按存储介质、线程模型、网络模型、数据结构、协议与持久化五面展开，§6 收口成一张成本账。

## 1. 纯内存操作：快的物理基础

- 所有数据常驻内存，读写路径**没有磁盘 IO**。内存随机访问约 100ns 量级，SSD 随机读约 100μs 量级，机械盘约 10ms 量级——介质差距就是三到五个数量级。
- 对比 MySQL：即便命中 Buffer Pool，仍要经过 B+ 树多层页寻址、MVCC 可见性判断、锁与日志；Redis 的 GET 就是一次哈希表查找。
- 代价同样明确：**内存贵且容量有限**，数据量突破单机内存就要上 Cluster 分片（见 [redis-cluster.md](./redis-cluster.md)）；内存易失，持久化是额外课题（§5）。

## 2. 单线程命令执行：不是缺陷而是结论

### 2.1 为什么单线程反而快

- **瓶颈不在 CPU**：GET/SET 是纯内存操作，单核每秒可执行千万次量级；真正的瓶颈是内存带宽与网络 IO。加线程执行命令不会更快，只会引入成本。
- **省掉三笔并发税**：无锁（不需要保护共享数据结构的互斥锁）、无上下文切换（不存在线程间调度）、无竞态（命令天然原子，`INCR`、`SETNX` 无须额外同步）。
- **单线程 ≠ 单进程线程**：Redis 一直有后台线程（bio）承担 AOF fsync、文件关闭等慢操作；4.0 起 `UNLINK`、异步 flush 等 lazyfree 操作也交给后台线程——**主线程只做"快活"，慢活全部外包**。

### 2.2 Redis 6.0 多线程 IO：只拆网络，不拆执行

6.0 引入 IO 线程（`io-threads`，默认 1 即关闭），把**socket 读写与协议解析**分摊到多个线程，命令执行仍是单线程：

- 动机：大流量下网络读写与 RESP 解析开始吃掉主线程 CPU，成为新瓶颈。
- 边界：多线程只覆盖"字节进出"，不覆盖"命令执行"——因此仍然无锁、仍然原子，2.1 的结论不被破坏。
- 这与 RocketMQ"IO 线程只做读写帧、业务逻辑独立派发"是同一设计哲学：**线程数与并发数解耦，执行模型保持串行简单**。

## 3. IO 多路复用：一个线程喂饱数万连接

- Redis 自研 ae 事件循环，Linux 下基于 **epoll**（macOS 为 kqueue），单线程同时监听数万连接的就绪事件，就绪一个处理一个。
- 对比"一连接一线程"模型：没有每连接的栈内存与调度开销，连接数与线程数彻底解耦；对比阻塞 IO：没有线程在等网络字节。
- 请求在事件循环里排队串行执行，配合 §2 的单线程模型，**并发连接数可以很大，命令执行永远有序**——这也是 Redis 事务与 Lua 脚本原子性的模型前提。
- 配套手段：**Pipeline** 把 N 条命令攒进一次网络往返，摊薄 RTT——与 RocketMQ 攒批发送同理，吞吐杠杆在客户端。

## 4. 高效数据结构：每条命令的寻址成本

Redis 为每种类型设计了"小数据紧凑、大数据高效"的双层编码：

| 类型 | 小数据编码 | 大数据编码 | 关键操作复杂度 |
|---|---|---|---|
| String | SDS（简单动态字符串） | 同左 | GET/SET O(1)，APPEND 均摊 O(1) |
| Hash | listpack（7.0 前为 ziplist） | hashtable | HGET/HSET O(1) |
| List | quicklist（listpack 节点 doubly-linked） | 同左 | 两端 LPUSH/RPUSH O(1) |
| Set | intset（全整数）/ listpack | hashtable | SADD/SISMEMBER O(1) |
| ZSet | listpack | skiplist + hashtable | ZADD/ZSCORE O(logN)，按成员查分值 O(1) |

- **全局键空间是一张 hashtable**（dict）：Key 定位 O(1)，扩容采用**渐进式 rehash**——把搬迁成本摊到后续每次读写，避免一次性 rehash 卡住单线程。
- **listpack/ziplist**：连续内存紧凑布局，无指针开销、缓存友好，小数据量下比指针结构更快更省；超过阈值自动升级为哈希表/跳表，避免 O(N) 扫描退化。
- **skiplist**：实现远比平衡树简单，范围查询（ZRANGEBYSCORE）天然友好，并发友好性虽用不上（单线程），但实现简单本身就是可靠性。
- **SDS**：预分配 + 惰性释放，杜绝 C 字符串的缓冲区溢出与每次 strlen 的 O(N) 扫描。

## 5. 协议与持久化：固定成本挪出关键路径

- **RESP 协议极简**：文本行协议，解析就是按 `\r\n` 切分与长度前缀读取，没有 Thrift/Protobuf 式的 schema 编解码成本；简单到可以用 telnet 手敲命令。
- **持久化不在写路径上**：
  - RDB：fork 子进程 + 写时复制（COW）生成快照，主线程只在 fork 瞬间有毫秒级停顿；
  - AOF：命令先写内存缓冲，`appendfsync everysec`（默认）由后台线程每秒 fsync 一次——写请求不等磁盘。
  - 对比 MySQL 的 redo log 组提交：Redis 干脆**默认不把持久性放进关键路径**，用"最多丢一秒数据"换吞吐。
- **C 语言实现、无 GC**：没有 JVM 停顿，内存布局手工可控；单线程模型下也不需要原子引用计数之类的并发设施。

## 6. 收口：一张成本账

| 固定成本 | 省掉/摊还机制 | 所在章节 |
|---|---|---|
| 磁盘 IO | 纯内存操作 | §1 |
| 锁竞争 / 上下文切换 / 竞态 | 命令执行单线程 | §2.1 |
| 慢操作阻塞主线程 | bio 后台线程 + lazyfree | §2.1 |
| 网络读写与协议解析 CPU | 6.0 IO 线程（可选） | §2.2 |
| 每连接线程开销 | epoll IO 多路复用 | §3 |
| RPC 往返 | Pipeline 攒批 | §3 |
| Key 寻址 | 全局 hashtable O(1) + 渐进式 rehash | §4 |
| 小对象指针开销 | listpack/intset 紧凑编码 | §4 |
| 协议编解码 | RESP 文本行协议 | §5 |
| fsync / 快照落盘 | AOF everysec 后台刷 + RDB fork COW | §5 |

**一句话收口**：Redis 的快 = 内存介质 × 单线程无锁模型 × epoll 高并发接入 × O(1) 寻址与紧凑编码 × 慢操作全部异步外包；五个因子相乘，任何一层退化（见 §7）都会把乘法变成短板。

## 7. 反面：什么会让 Redis 慢下来

单线程是双刃剑——**任何一条慢命令都会阻塞所有请求**：

- **大 Key**：对百万元素的 Hash 执行 `HGETALL`、对大 List 执行 `LRANGE 0 -1`，O(N) 操作独占主线程，毫秒级变秒级；删除大 Key 用 `UNLINK` 而非 `DEL`（lazyfree 外包）。
- **O(N) 命令**：`KEYS *` 全库扫描，生产禁用，用 `SCAN` 渐进遍历替代。
- **网络 RTT**：单条命令的耗时大头往往在网络往返而非服务端执行——这正是 Pipeline 与"就近部署"的价值。
- **fork 停顿**：内存越大 fork 页表拷贝越久，RDB/AOF rewrite 瞬间的毛刺来源。
- **AOF always**：`appendfsync always` 把 fsync 拉回关键路径，吞吐骤降——持久性与吞吐的显式取舍。
- **内存换页（swap）**：数据被换出到磁盘，内存操作退化为磁盘 IO，§1 的物理基础崩塌。
