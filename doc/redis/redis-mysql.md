# Redis 与 MySQL 数据一致性：从双写竞态到 Binlog 订阅

> 主题边界：简历写「熟练使用 MySQL、Redis 进行应用开发」，面试官几乎必然追问**缓存与数据库的数据一致性**——这是检验"会用"还是"懂原理"的分水岭问题。本文只讨论同一份数据在 Redis 与 MySQL 两个异构存储间的一致性保障，不涉及 Redis 主从复制一致性。缓存三大经典问题见 [redis-cache-penetration.md](./redis-cache-penetration.md) 系列。

---

## 1. 为什么会不一致：双写不是原子操作

同一份数据存两处（MySQL 权威、Redis 加速），任何更新都要**双写**，而双写天然面临三个问题：

1. **非原子**：两步操作之间必然存在时间窗口，窗口内两处数据不同；
2. **并发交错**：多个读写请求的双写步骤互相穿插，顺序无法保证；
3. **部分失败**：第一步成功、第二步失败（进程崩溃、网络抖动），不一致被固化。

先穷举四种双写顺序，理解为什么主流方案是「先更 DB 再删缓存」：

| 顺序              | 问题                                                                |
|-------------------|---------------------------------------------------------------------|
| 先更缓存，再更 DB | DB 更新失败则缓存是脏数据；并发写时后更 DB 的值可能被先更的缓存覆盖 |
| 先更 DB，再更缓存 | 并发写时两个请求的「更 DB」与「更缓存」交错，缓存可能留下旧值       |
| 先删缓存，再更 DB | 删后更前的窗口内，读请求 miss 后把**旧值**回填缓存，脏数据长期驻留  |
| 先更 DB，再删缓存 | 不一致窗口最短，仅在极端交错下出现（见第 2 节），**主流选择**       |

两条关键设计原则：

- **删除优于更新**：缓存值可能是多表聚合、计算加工后的结果，每次写都重算并更新缓存是无效功（写多读少时大量更新根本不会被读到）；删除后由下一次读按需重建，即**懒加载**思想。同时"更新缓存"在并发写下极易互相覆盖，删除则天然幂等。
- **DB 先于缓存**：MySQL 是权威数据源，先让权威侧落定，再让加速侧失效，方向不能反。

## 2. Cache Aside Pattern：主流方案与它的真实竞态

旁路缓存模式（Cache Aside）是读多写少场景的标准答案：

- **读**：先读缓存，命中直接返回；miss 则查 DB，把结果回填缓存（建议带 TTL）；
- **写**：先更新 DB，成功后删除缓存。

```java
// 读路径
public User getUser(long id) {
    String key = "user:" + id;
    User user = redis.get(key);
    if (user != null) {
        return user;
    }
    user = mysql.selectById(id);
    redis.set(key, user, Duration.ofMinutes(30)); // TTL 兜底
    return user;
}

// 写路径
public void updateUser(User user) {
    mysql.update(user);   // 1. 先更新权威数据源
    redis.del("user:" + user.getId()); // 2. 再删除缓存
}
```

**真实竞态在哪里？** 常见误答是"写后立刻读到旧值"——先更 DB 再删缓存恰恰不存在这个问题。真正的竞态是**读 miss 回填与写路径的交错**：

1. 读请求 A 缓存 miss（如 Key 恰好过期），查 DB 得到旧值 v1；
2. 写请求 B 更新 DB 为 v2，删除缓存（此时缓存本来就是空的，删除无效果）；
3. 读请求 A 把 v1 回填缓存——脏数据驻留直到 TTL 到期。

发生概率极低：要求读请求的「查 DB + 回填」恰好横跨写请求的「更 DB + 删缓存」，而读 DB 通常远快于写 DB（写有锁、有事务、有刷盘），且缓存恰好处于失效状态。工程上认为可接受，配合 TTL 即可自愈；面试时能画出这个时序图并说清概率前提，才是加分项。

## 3. 延迟双删：压缩脏读窗口

针对「先删缓存再更 DB」的脏读窗口、或读写分离下从库延迟导致的旧值回填，可采用延迟双删：

```
删缓存 → 更新 DB → 延迟 N 毫秒 → 再删一次缓存
```

第二次删除清掉延迟窗口内被并发读回填的旧值。两个工程要点：

- **延迟时长**：N 需覆盖「一次读请求查 DB + 回填」的耗时；读写分离场景还要加上主从复制延迟，只能估算，无法精确。
- **第二次删除必须异步化**：主链路 sleep 会拖垮吞吐，应交给延迟队列（MQ 延迟消息 / 定时线程池）执行，主流程更完 DB 即返回。

延迟双删本质仍是**最终一致**：两次删除之间读到的仍是旧值，且第二次删除也可能失败——它只是把不一致窗口压缩，没有消除。

## 4. 删除失败怎么办：MQ 异步重试

Cache Aside 的软肋是第二步「删缓存」可能失败，失败即固化不一致。把删除动作交给 MQ 重试：

```
更新 DB → 发送删除消息 → 消费者删缓存 → 失败则重试（直到成功或人工介入）
```

但这里有一个容易被追问的**套娃问题**：「更新 DB」与「发消息」又是一次双写，如何保证两者同时成功？两种标准解法：

- **事务消息**（RocketMQ）：先发半消息 → 执行本地事务（更 DB）→ commit/rollback 半消息，Broker 回查兜底；
- **本地消息表**：消息与业务数据在**同一个本地事务**中落库，后台任务扫描待发送消息投递 MQ，成功后标记完成。

两者都把「跨系统双写」转化为「本地事务 + 异步补偿」，代价是引入 MQ 依赖与消息幂等处理（删除天然幂等，重试友好）。

## 5. 架构级解法：订阅 Binlog（Canal）

前述方案都在业务代码里做补偿，侵入性强且时序靠人肉推理。更彻底的做法是**让数据变更事件从权威源头自然流出**：

```
业务代码只更新 MySQL → Canal 伪装从库订阅 Binlog → 投递 MQ → 消费者更新/删除 Redis
```

- **零侵入**：业务代码不再关心缓存维护，双写问题从根上消失（只写 DB 一处）；
- **顺序权威**：Binlog 是 MySQL 事务提交的**串行化日志**，同一行的变更顺序天然与 DB 一致。消费端按 Key 分区保序后，甚至可以安全地用 **SET 回填**而非删除——因为事件携带的就是该行的最新值，不存在旧值覆盖新值的交错；
- **代价**：多一套 Canal + MQ 组件的运维成本，链路延迟从毫秒级变为几十毫秒到秒级，且需处理 Binlog 位点管理、消费幂等。

适合缓存数据面广、写入频繁、愿意为架构整洁付出组件成本的中大型系统。

## 6. 要强一致怎么办：读写锁与串行化

以上全部是**最终一致**方案。若业务真的要求「写成功之后任何读都不能见旧值」：

- **分布式读写锁**（Redisson `RReadWriteLock`）：写路径加写锁（更 DB + 删缓存期间排斥一切读），读 miss 回填路径加读锁。同一 Key 的读写被串行化，竞态窗口消失；
- **按 Key 串行化**：同一 Key 的读写请求路由到同一队列/线程顺序执行，思路等价，粒度更细。

代价是吞吐急剧下降——缓存本为性能而生，加锁后热点 Key 的性能可能还不如直接查 DB。且注意：**分布式锁本身并非线性一致**（主从切换可能丢锁，Redlock 亦有争议），它给出的仍是工程意义上的强一致。

真正的金融级做法往往是**釜底抽薪**：余额、库存扣减这类强一致数据**不进缓存**，直接读 DB（或走 DB 原子操作），缓存只服务容忍短暂陈旧的数据。一致性方案选型的最高境界是识别出哪些数据根本不该双写。

## 7. TTL：所有方案的兜底

无论选哪条路线，**缓存必须设置合理的 TTL**：它是唯一不依赖任何组件正常工作的自愈机制——即使删除失败、消息丢失、Canal 挂掉，脏数据最多存活一个 TTL 周期。TTL 时长即业务承诺的不一致上界，按数据容忍度设定（分钟级常见，秒级用于准实时场景）。

### 选型总表

| 方案              | 一致性级别 | 侵入性 | 额外组件   | 适用场景                         |
|-------------------|------------|--------|------------|----------------------------------|
| Cache Aside + TTL | 最终一致   | 低     | 无         | 读多写少的绝大多数业务（默认选） |
| 延迟双删          | 最终一致   | 中     | 延迟队列   | 读写分离从库延迟、脏读窗口敏感   |
| MQ 异步重试       | 最终一致   | 中     | MQ         | 删除失败不可接受、已有 MQ 设施   |
| Canal 订阅 Binlog | 最终一致   | 零     | Canal + MQ | 缓存面广、写入频繁的中大型系统   |
| 分布式读写锁      | 工程强一致 | 高     | Redisson   | 少量关键 Key，可牺牲吞吐         |
| 不缓存            | 强一致     | —      | 无         | 余额、库存等金融级数据           |
